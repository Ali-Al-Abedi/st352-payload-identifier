# Audit 0x94 / 0x95 / 0x96 / 0x97 / 0x98 — SMPTE ST 425-3:2019 / ST 425-5:2019

| Field    | Value |
| -------- | ----- |
| Family   | Dual-link 3G-SDI (ST 425-3) and Quad-link 3G-SDI (ST 425-5) |
| Spec(s)  | `audit/pdf-text/st425-3-2019.txt` (ST 425-3:2019) sections 6.2.3 / 7.2.3 / 8.2.3<br>`audit/pdf-text/st425-5-2019.txt` (ST 425-5:2019) sections 6.2.3 / 7.2.3 |
| Code(s)  | 0x94, 0x95, 0x96, 0x97, 0x98 |

## Scope

Five Byte 1 codes covering the entire ST 425-3 / ST 425-5 family:

- 0x94 — Dual-link 3G-A 1080-line HFR (ST 425-3 section 6.2.3)
- 0x95 — Dual-link 3G-B-DL 1080-line HFR (ST 425-3 section 7.2.3)
- 0x96 — Dual-link 3G-B-DS 2160-line LFR (ST 425-3 section 8.2.3)
- 0x97 — Quad-link 3G-A 2160-line UHD (ST 425-5 section 6.2.3)
- 0x98 — Quad-link 3G-B-DL 2160-line UHD (ST 425-5 section 7.2.3)

## Findings

### P0: All five layouts have BROKEN round-trip

All round-trip vectors fail. Symptom is identical to the ST 2036-3/-4, ST 435-1, ST 425-1 and stereoscopic audits: the
encoder consumes raw numeric bit fields (c.rate, c.samp, c.colorim, c.bitDepth, ...) but the decoder populates
human-readable strings ("10-bit", etc.) instead.

Probe evidence:

```
RT 94 CA 80 01: MISMATCH  (got CC 80 00, want CA 80 01)
RT 95 4A 00 01: MISMATCH  (got 4A 00 00, want 4A 00 01)
RT 96 06 00 01: MISMATCH  (got 0A 00 00, want 06 00 01)
RT 97 CA 80 01: MISMATCH  (got CA 80 00, want CA 80 01)
RT 98 4A 00 01: MISMATCH  (got 4A 00 00, want 4A 00 01)
```

Fix: expose `rate`, `samp`, `colorim`, `colorimSplitBits`, `aspectBit`, `hSampBit`, `tcBits`, `signalBit`,
`linkAssignment`, `dataStream`, `audioCopy`, `depthBits` raw numeric fields in `characteristics`; update each
`encode()` to prefer the raw fields with backward-compatible string fallbacks.

### P1: 0x94/0x95/0x96/0x97/0x98 — missing reserved/mandatory-bit warnings

Per the relevant sections of ST 425-3 / ST 425-5, every layout has a number of bits or values that are reserved
or mandatory, but the implementation does not warn when they are violated:

| 0x94 | ST 425-3 6.2.3.3   | b7 (Byte 2) shall be 1 (progressive transport)        | NOT enforced |
| 0x94 | ST 425-3 6.2.3.3   | b6 (Byte 2) shall be 1 (progressive picture)          | NOT enforced |
| 0x94 | ST 425-3 6.2.3.3   | Byte 2 b3:b0 shall be in {4h, 8h, 9h, Ah, Bh}         | NOT enforced |
| 0x94 | ST 425-3 6.2.3.4   | Byte 3 b3:b0 only Table 8a permitted values           | NOT enforced |
| 0x94 | ST 425-3 6.2.3.5   | Byte 4 b7=0, b5=0, b3=0 (all reserved)                | NOT enforced |
| 0x95 | ST 425-3 7.2.3.3   | Byte 2 b7=0 (interlaced transport mandatory)          | NOT enforced |
| 0x95 | ST 425-3 7.2.3.3   | Byte 2 b6=1 (progressive picture)                     | NOT enforced |
| 0x95 | ST 425-3 7.2.3.3   | Byte 2 b3:b0 shall be in {4h, 8h, 9h, Ah, Bh}         | NOT enforced |
| 0x95 | ST 425-3 7.2.3.4   | Byte 3 b3:b0 only Table 8a permitted values           | NOT enforced |
| 0x95 | ST 425-3 7.2.3.5   | Byte 4 b5=0, b3=0 (reserved)                          | NOT enforced |

| 0x96 | ST 425-3 8.2.3.3   | Byte 2 b3:b0 shall be in {2h, 3h, 5h, 6h, 7h}         | NOT enforced |

Fix: add explicit `warnings.push(...)` calls in each decode for every violation listed above.

### P2: 0x94 and 0x97 — colorimetry 1h reported as "Reserved"

Per ST 425-3 section 6.2.3.4 (Table 8) and ST 425-5 section 6.2.3.4 (Table 6), Byte 3 b5:b4 = 1h identifies the
"Color VANC Packet as defined in SMPTE ST 2048-1". The current global `COLORIMETRY_2BIT[1]` table is overridden
to "Reserved" because of the post-2017 revision of ST 425-1, but ST 425-3:2019 / ST 425-5:2019 explicitly retain
the "Color VANC Packet" semantics for these specific Level A layouts.

Probe evidence:

```
--- 94 CA 90 01  colorim 1h = Color VANC Packet (ST 425-3) ---
  COLOR: Reserved | TC=SDR-TV   <-- incorrect
--- 97 CA 90 01  colorim 1h = Color VANC Packet (ST 425-5) ---
  COLOR: Reserved | TC=SDR-TV   <-- incorrect
```

Fix: in the 0x94 and 0x97 decoders, override `colorimetry` to "Color VANC Packet (ST 2048-1)" when
`colorim === 0x1`. Do NOT add a "Reserved" warning for these codes.

### P2: 0x96 / 0x98 — split-colorimetry 1h is "Color VANC Packet"

ST 425-3 section 8.2.3.4 (0x96) and ST 425-5 section 7.2.3.4 (0x98) explicitly define b7,b4 = 1h as
"Color VANC Packet" (in their split-bit colorim layouts). The global `COLORIMETRY_SPLIT[1]` says "Reserved"
which is correct for 0x95 (ST 425-3 7.2.3.4 says only 0h/2h/3h are defined) but wrong for 0x96/0x98.

Fix: in 0x96 and 0x98 decoders, override colorimetry label to "Color VANC Packet (ST 2048-1)" when split-bit
colorim resolves to 1h. Do NOT add a "Reserved" warning.

## Resolution

All P0 and P1 issues addressed in the same pass:

- Round-trip restored by exposing raw numeric bit fields in characteristics and rewriting each `encode()` to prefer them.
- Mandatory/reserved warnings added per ST 425-3 / ST 425-5 sections.
- Colorim-1h override added for 0x94/0x97 (modern 2-bit) and 0x96/0x98 (split-bit).

After the fixes all probe round-trip cases pass, all expected warnings are emitted, and colorim-1h is reported correctly.
