### 0xA2 — UHDTV2 (7680×4320) over quad/octa-link 10G-SDI Mode D — ST 2036-3 Table 7

- Word 3 b7 is "Reserved" (must be 0), b6:b4 is the 3-bit link number (0..7) instead of 1-bit + Reserved.

### 0xA6 — UHDTV2 (7680×4320) — inherits Word 2 / Word 3 / Word 4 from 0xA5

The 0xA6 layout in code calls `VPID_LAYOUTS[0xA5].decode()` and patches resolution, interface,
standard label, and the user-facing channel string. All bit-level decoding/warnings inherit
correctly.

## Findings & Fixes

| # | Severity | Affected codes | Description | Fix |
|---|----------|----------------|-------------|-----|
| 1 | P2 | 0xA1, 0xA2, 0xA5, 0xA6 | `characteristics.scan` reported "Interlaced" for PsF carriage of progressive picture (b7=0, b6=1). Spec mandates picture is always progressive. Same family of bug as 0xB3 (ST 2048-3). | Updated to `pic ? (trans ? "Progressive" : "Progressive (PsF)") : "Interlaced (invalid)"` so the picture's actual scan type is reported. |
| 2 | P2 | 0xA5, 0xA6 | Picture-rate values 0h (Undefined), 1h (Reserved) emitted no warning. Only 4h, 8h, Ch were warned. ST 2036-4 Table 9 explicitly lists 0h as "Undefined" and 1h as "Reserved", and the comment incorrectly listed valid range as "0-3" which suggested 0h and 1h were OK. | Added explicit warnings for rate==0h ("Undefined") and rate==1h ("Reserved"). Updated comment to match Table 9. |
| 3 | P2 | 0xA1, 0xA2, 0xA5, 0xA6 | `decode → encode` round-trip was broken. `encode()` expected raw numeric fields (`c.rate`, `c.samp`, numeric `c.channel`, `c.transferChar`, numeric `c.bitDepth`) that `decode()` never set on `characteristics` (decode set human-friendly strings like `transferChar: "SDR"`, `channel: "Single/Link 1 / Ch1"`). The encoder produced `00 00` for bytes 3-4 instead of the original. | Added raw bit fields to decode characteristics (`rate`, `samp`, `chAssignment`, `linkAssignment`, `colorimBit`, `signalBit`, `depthBits`, `tcBits`, `transBit`, `picBit`) and made `encode()` prefer these numerics, with backward-compatible fallbacks to the human-friendly fields and the existing UI-extractor shape (`linkAssignment` numeric / `c.transferChar` lookup by code, etc.). |
| 4 | P3 | 0xA5, 0xA6 | Round-trip side note: when the input has `byte 3 b0 = 1` (Reserved), the encoder normalises it to `0`. This is correct behaviour (Reserved bits must be 0 on encode), so the decode→encode bytes do not exactly match the (illegal) input. The warning correctly fires. Tracked here for awareness, not as a bug. | None — this is intended normalisation. |
