# Audit: 0x88 / 0x89 — SMPTE ST 425-1:2017

**Spec under audit**: SMPTE ST 425-1:2017 §4.1.6 (Source image format
identification), Tables 4 / 5 / 6 (byte 2 / byte 3 / byte 4 layout).
**Layouts audited**: `0x88` (3G-SDI Level A 720-line),
`0x89` (3G-SDI Level A 1080-line).
**Companion codes audited (delegated layouts)**:
- `0x8A` (3G-B-DL → ST 372 / `0x87`)
- `0x8B` (3G-B-DS 720 → ST 292-1 720 / `0x84`)
- `0x8C` (3G-B-DS 1080 → ST 292-1 1080 / `0x85`)
- `0x8D` (3G-B-DS SD → ST 352 §B.1 / `0x81`)

`0x8A`–`0x8D` carry no ST 425-1-specific bit-level changes; they reuse the
referenced layouts byte-for-byte. Their decoders/encoders correctly
delegate. Audit findings for those layouts will be captured in the
ST 372 / ST 292-1 / ST 352 audits.

## Findings

### F-425-1-01 — `0x88` byte 3 fields incorrectly lumped as "Reserved" (P1)
**Spec**: ST 425-1:2017 §4.1.6.2.2 / Table 5 — for 750-line (`0x88`),
byte 3 carries:
- b7  Aspect ratio (1 = 16:9)
- b6  Reserved (would be horizontal-pixel-count for 1080-line)
- b5:b4 Colorimetry (Rec.709 / Reserved / Rec.2020 / Unknown)
- b3:b0 Sampling structure

**Bug**: Decoder reported the entire upper nibble (`b7:b4`) as a single
"Reserved" field, hiding aspect ratio and colorimetry. The
`characteristics.aspect` field was hard-coded to `"16:9"` regardless of
b7, and `characteristics.colorimetry` was hard-coded to "Rec. 709
(assumed)" with a deliberately misleading comment.

**Fix**: Split byte 3 into the four real fields, expose
`aspectBit` / `colorimBits` raw values for round-trip, warn on
`b6 = 1` and on `colorim == 1h` (Reserved). Field display also
reports actual aspect ("16:9" or "Unknown") rather than hard-coding.

### F-425-1-02 — `0x88`/`0x89` byte 4 fields incorrectly lumped as "Reserved" (P1)
**Spec**: ST 425-1:2017 §4.1.6.2.3 / Table 6 — byte 4 carries:
- b7:b5 Reserved (must be 0)
- b4    Luminance/colour signal (0 = Y'CbCr, 1 = ICtCp per BT.2100)
- b3:b2 Reserved (must be 0)
- b1:b0 Bit depth (0 = 10-bit FR, 1 = 10-bit, 2 = 12-bit, 3 = 12-bit FR)

**Bug**: Both `0x88` and `0x89` decoders reported `b7:b2` as a single
"Reserved" field, completely hiding the ICtCp / Y'CbCr signal-type bit.
This made BT.2100 ICtCp signals indistinguishable from Y'CbCr in the
decoded output.

**Fix**: Split byte 4 into b7:b5 / b4 / b3:b2 / b1:b0 fields with
individual reserved-bit warnings; expose `signalBit` and `depthBits`
raw values for round-trip; show "ICtCp (BT.2100)" vs "Y'CbCr" in the
field list and override the sampling label so the user-visible
`characteristics.sampling` reflects ICtCp when set.

### F-425-1-03 — Missing colorimetry-1h Reserved warning (P2)
**Spec**: ST 425-1:2017 Table 5 colorimetry codes:
- 0h = Rec.709 — 1h = Reserved — 2h = Rec.2020 (UHDTV) — 3h = Unknown

**Bug**: Decoder accepted `colorim = 1h` silently and the global
`COLORIMETRY_2BIT[0x1].label` was set to "Color VANC packet" — a label
that only applies to the older split-bit encoding (ST 292-1 / ST 372).
For all post-2017 layouts (`0x88` / `0x89` / ST 425-3 / ST 425-5 /
ST 2082-* / BT.2077-*), value 1h is *Reserved*.

**Fix**:
1. Updated `COLORIMETRY_2BIT[0x1]` to label "Reserved" with citation
   note pointing back to ST 425-1:2017 §6.4.3.
2. Added explicit warning in both `0x88` and `0x89` decoders when
   `colorim == 1h`.
The split-bit table `COLORIMETRY_SPLIT[0x1]` remains "Color VANC
packet" as that legacy meaning is still defined for ST 292-1 / ST 372 /
ST 425-2 / ST 425-4 / ST 425-6.

### F-425-1-04 — Missing reserved-sampling-code warnings (P2)
**Spec**: ST 352:2013 Table 3 marks codes Bh, Ch, Dh, Fh as Reserved.
ST 425-1 Table 5a allows only 0h/1h/2h/3h/4h/5h/6h/7h/8h/9h/Ah/Eh.

**Bug**: Decoder silently displayed "Reserved" as the sampling label
for these codes without adding a warning.

**Fix**: Added explicit `warnings.push()` for sampling values Bh, Ch,
Dh, Fh in both `0x88` and `0x89`.

### F-425-1-05 — Missing picture-rate Undefined / Reserved warnings (P2)
**Spec**: ST 352:2013 Table 2: rate 0h = "Undefined", rate 1h =
"Reserved". Both are non-normative; production sources must signal a
defined rate.

**Bug**: Decoder accepted these silently and showed "Not defined" /
"96/1.001 (95.904)" labels with no warning.

**Fix**: Added explicit warnings for rate 0h and 1h in both decoders.

### F-425-1-06 — Missing transport/picture-bit-combination warning for `0x89` (P2)
**Spec**: ST 425-1 Table 4 defines only three transport/picture
combinations:
- 00b = Interlaced transport, Interlaced picture (1080i)
- 01b = Interlaced transport, Progressive picture (1080PsF on interlaced
        transport)
- 11b = Progressive transport, Progressive picture (1080p)
The 10b combination (`b7=1, b6=0`) is not defined — only `0x88`/`0x89`
3G-A reuse it informally for "PsF/Interlaced" non-canonical signalling.

**Bug**: `0x89` decoder accepted 10b silently, returning
`scan = "PsF/Interlaced (3G-A)"` without flagging that it falls outside
the ST 425-1 normative table.

**Fix**: Added warning when `trans = 1, pic = 0` for `0x89`.

### F-425-1-07 — Broken `decode → encode` round-trip (P1)
**Spec**: A correctly decoded VPID must encode back to the same byte
sequence.

**Bug**: The pre-fix encoders for `0x88` / `0x89` consumed string-form
characteristics (e.g. `c.aspect === "16:9"` → 1) but never read the
ICtCp signal bit, the byte 3 b6 reserved bit (0x88), or the
horizontal-pixel-count bit `c.horizontalActive === 2048` (the property
was named `c.hSamp` in the encoder but the decoder set
`horizontalActive`). Result: round-trip dropped the signal-type bit
and any 2048-line variant got encoded as 1920.

**Fix**: Rewrote both encoders to *prefer* the new raw bit fields
(`aspectBit`, `hSampBit`, `colorimBits`, `signalBit`, `depthBits`,
`tcBits`, `rate`, `samp`) when present, with backward-compatible
fallbacks to the human-friendly strings.

## Validation

- `tests/extract_vpid_js.py` includes new vectors covering:
  - `88 CA 80 02` / `88 CA 80 12` (canonical and ICtCp)
  - `88 CA 50 01` / `88 CA 10 01` / `88 CA 00 04` (warning vectors)
  - `89 CA 80 01` / `89 CA 80 11` / `89 CA E0 02`
  - `89 80 80 01` / `89 CA 0B 01` / `89 C0 80 01` / `89 C1 80 01`
- A focused round-trip probe (`/tmp/probe_88_89.js`) confirms 9/9
  round-trip vectors are byte-exact for the canonical formats.
- All previous self-tests continue to pass.
