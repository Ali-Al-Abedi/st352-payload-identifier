# Audit 0x87 — SMPTE ST 372:2017

| Field    | Value |
| -------- | ----- |
| Family   | Dual-link 1.5 Gb/s HD-SDI (1080-line) |
| Spec     | `audit/pdf-text/st0372-2017.txt` (ST 372:2017) §7 / Table 5 / Table 6 |
| Code     | 0x87 |

## Scope

A single Byte 1 code covering the whole ST 372:2017 family:

- 0x87 — Dual-link 1.5 Gb/s HD-SDI 1080-line payload (ST 372:2017 §7).

ST 372 carries 1080-line video on two paired 1.485 Gb/s links (Link A / Link B) and supports
1920×1080 and 2048×1080 picture sizes, all four ST 274 / ST 2048-2 progressive frame rates,
SDR / HLG / PQ transfer characteristics (since the 2017 revision), Rec.709 / UHDTV / X'Y'Z'
colorimetry (split-bit), and 10/12-bit quantisation in Full Range or Narrow Range. It is the
only "dual link" code with a dedicated Byte 1, distinguishing it from ST 425-3 dual-link 3G-SDI.

## Findings

### P0: BIT_DEPTH_HD_1080 table is wrong for ST 372:2017 — 12-bit support silently missing

The shared `BIT_DEPTH_HD_1080` constant maps:

```
0h → "8-bit"
1h → "10-bit"
2h → "10-bit Full Range"
3h → "Reserved"
```

…which is the legacy ST 292-1 1080-line mapping. ST 372:2017 §7.4 (Table 5) explicitly redefines
this field for 0x87:

```
0h → 10-bit Full Range
1h → 10-bit
2h → 12-bit
3h → 12-bit Full Range
```

Probe evidence:

```
--- 87 CA 00 02  EXPECT 12-bit per ST 372 §7.4 ---
  BD: 10-bit Full Range          <-- WRONG, should be "12-bit"
--- 87 CA 00 03  EXPECT 12-bit FR per ST 372 §7.4 ---
  BD: Reserved                    <-- WRONG, should be "12-bit Full Range"
--- 87 CA 00 00  EXPECT 10-bit FR per ST 372 §7.4 ---
  BD: 8-bit                       <-- WRONG, should be "10-bit Full Range"
```

Two of the four bit-depth code points are silently misreported for 0x87 — for instance, a true
12-bit Full Range payload (depth = 3h) is silently displayed as "Reserved" with no warning, and a
12-bit narrow payload is misreported as "10-bit Full Range". This will mislead operators about the
actual quantisation of incoming 1080-line dual-link feeds.

Note: the same global table is also wired into 0x85 (ST 292-1:2018 §9.5.6), 0x95 (ST 425-3:2019
§7.2.3.5), 0x96 (ST 425-3:2019 §8.2.3.5), and 0x98 (ST 425-5:2019 §7.2.3.5). Each of those specs
has its **own** bit-depth table, which the upcoming ST 292-1 audit will address. To keep this
audit narrowly scoped, this fix introduces a new `BIT_DEPTH_ST372` constant for 0x87 only.

Fix: introduce `BIT_DEPTH_ST372` (10FR / 10 / 12 / 12FR) and use it from the 0x87 decoder/encoder.

### P0: 0x87 round-trip is BROKEN

All non-trivial round-trip vectors fail. Symptom is the same pattern uncovered in every previous
audit: the encoder consumes raw numeric bit fields (`c.rate`, `c.colorim`, `c.transferChar`,
`c.hSamp`, `c.samp`, `c.bitDepth`) but the decoder populates string labels (`"59.94"`, `"HLG"`,
`"10-bit"`, `2048` not exposed at all) instead.

Probe evidence:

```
RT 87 CA 00 01: MISMATCH  (got CA 00 00, want CA 00 01)   <-- Rec.709 10-bit Link A
RT 87 CA 00 41: MISMATCH  (got CA 00 40, want CA 00 41)   <-- Link B
RT 87 4A 00 01: MISMATCH  (got 4A 00 00, want 4A 00 01)   <-- PsF
RT 87 CA 00 02: MISMATCH  (got CA 00 00, want CA 00 02)   <-- 12-bit
RT 87 CA 00 03: MISMATCH  (got CA 00 00, want CA 00 03)   <-- 12-bit FR
RT 87 DA 00 01: MISMATCH  (got CA 00 00, want DA 00 01)   <-- HLG
RT 87 EA 00 01: MISMATCH  (got CA 00 00, want EA 00 01)   <-- PQ
RT 87 CA 60 01: MISMATCH  (got CA 20 00, want CA 60 01)   <-- 2048×1080
RT 87 CA 20 01: MISMATCH  (got CA 20 00, want CA 20 01)   <-- 16:9
RT 87 CA 00 11: MISMATCH  (got CA 00 00, want CA 00 11)   <-- ICTCP signal
RT 87 CA A0 01: MISMATCH  (got CA 20 00, want CA A0 01)   <-- Rec.2020 (split colorim)
RT 87 CA B0 01: MISMATCH  (got CA 20 00, want CA B0 01)   <-- Unknown (split colorim)
```

Fix: expose `rate`, `samp`, `colorim`, `tcBits`, `aspectBit`, `hSampBit`, `signalBit`, `linkBit`,
`depthBits`, `transBit`, `picBit` raw numeric fields in `characteristics`; update `encode()` to
prefer those raw fields with backward-compatible string fallbacks.

### P1: Byte 4 b4 (Y'CbCr / ICTCP signal-type indicator) is not decoded

ST 372:2017 §7.4 defines Byte 4 b4 explicitly:

> b4 = 0 indicates that the Y′C′BC′R sampling structure defined in Byte 3 bits b3:b0, is interpreted as Y′C′BC′R.
> b4 = 1 indicates that the Y′C′BC′R sampling structure defined in Byte 3 bits b3:b0, is interpreted as ICTCP in accordance with Recommendation ITU-R BT.2100.

The current decoder lumps `b5:b2` together as a single "Reserved" field, which silently masks the
ICTCP indicator. A genuine ICTCP feed (b4 = 1) is decoded as ordinary Y'CbCr, with no warning.

Probe evidence:

```
--- 87 CA 00 11  ICTCP (byte 4 b4=1) ---
  signal: -                       <-- silently dropped
```

Fix: split byte 4 into per-bit fields:
- b7 — Reserved
- b6 — Link A/B
- b5 — Reserved
- b4 — Signal type (Y′C′BC′R vs ICTCP)
- b3 — Reserved
- b2 — Reserved
- b1:b0 — Bit depth

Add a `signalType` field to `characteristics` (`"Y'CbCr"` / `"ICTCP"`).

### P1: Missing reserved-bit warnings on Byte 4 b7 / b5 / b3 / b2

Per ST 372:2017 §7.4 / Table 5, Byte 4 bits b7, b5, b3, b2 are all marked Reserved and "shall be
set to zero". Currently the decoder lumps b7 and b5:b2 together, but no warning is emitted when
any individual bit is non-zero (the lumped field is only flagged when the *combined* value is
non-zero, which makes it impossible for a downstream user to distinguish, say, an erroneous b3
from a legitimate ICTCP indicator on b4).

Probe evidence:

```
--- 87 CA 00 81  byte4 b7=1 ---  (no warnings)
--- 87 CA 00 21  byte4 b5=1 ---  (no warnings)
--- 87 CA 00 09  byte4 b3=1 ---  (no warnings)
--- 87 CA 00 05  byte4 b2=1 ---  (no warnings)
```

Fix: emit per-bit warnings when any of b7, b5, b3, b2 is set.

### P2: Colorimetry 1h is reported as "Color VANC packet" instead of "Reserved"

ST 372:2017 §7.3 enumerates the only defined colorimetry code-points (split bits b7,b4):

```
0h identifies Rec 709 colorimetry
2h identifies UHDTV colorimetry (BT.2020 primaries)
3h identifies unknown colorimetry
```

…and explicitly says **"Other values are reserved"**. The implementation, however, falls back to
the global `COLORIMETRY_SPLIT` table, which still reports 1h as `"Color VANC packet"` (the legacy
pre-2017 ST 425-1 split-bit semantic). For 0x87 this is incorrect.

Probe evidence:

```
--- 87 CA 10 01  colorim 1h Reserved ---
  COLOR: Color VANC packet        <-- should be "Reserved" + warn
```

Fix: in the 0x87 decoder, override the colorimetry label to "Reserved (per ST 372:2017 §7.3)"
when `colorim === 0x1`, and push a warning.

### P2: Reserved sampling-structure values (Bh / Ch / Dh / Fh) emit no warning

Per ST 372:2017 Table 6, sampling values Bh, Ch, Dh, Fh are all "Reserved". The decoder happily
returns `"Reserved"` from the global `SAMPLING` table but does not push a warning. Without a
warning, an out-of-spec stream is silently treated as legal.

Probe evidence:

```
--- 87 CA 0B 01  sampling Bh ---
  SAMP: Reserved                  <-- no warning
--- 87 CA 0F 01  sampling Fh ---
  SAMP: Reserved                  <-- no warning
```

Fix: emit a warning for `samp ∈ {Bh, Ch, Dh, Fh}`.

## Resolution

All findings are addressed in the same pass:

- New `BIT_DEPTH_ST372` constant (10FR / 10 / 12 / 12FR) per ST 372:2017 §7.4 Table 5.
- 0x87 decoder rewritten to:
  - use `BIT_DEPTH_ST372`;
  - split Byte 4 into per-bit fields (`b7`, `b6` link, `b5`, `b4` signal type, `b3`, `b2`, `b1:b0` depth);
  - emit reserved-bit warnings on b7, b5, b3, b2;
  - emit warnings for `colorim === 0x1` (override label to "Reserved");
  - emit warnings for sampling Bh / Ch / Dh / Fh;
  - expose raw numeric fields (`rate`, `samp`, `colorim`, `tcBits`, `aspectBit`, `hSampBit`,
    `signalBit`, `linkBit`, `depthBits`, `transBit`, `picBit`) in `characteristics`.
- 0x87 encoder rewritten to prefer raw numeric fields (with string fallbacks for backward
  compatibility with the dropdown UI).

After the fixes, all probe round-trip cases pass and all expected warnings are emitted.
