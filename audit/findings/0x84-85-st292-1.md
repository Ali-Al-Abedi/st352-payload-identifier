# Audit 0x84 / 0x85 — SMPTE ST 292-1:2018

| Field    | Value |
| -------- | ----- |
| Family   | 1.485 Gb/s HD-SDI (single link) |
| Spec     | `audit/pdf-text/st292-1-2018.txt` (ST 292-1:2018) §9.4 (0x84) / §9.5 (0x85) |
| Code(s)  | 0x84, 0x85 |

## Scope

Two Byte 1 codes covering the entire ST 292-1:2018 family:

- 0x84 — 720-line progressive payloads on a 1.485 Gb/s SDI (ST 292-1:2018 §9.4).
- 0x85 — 1080-line interlaced/progressive/PsF payloads on a 1.485 Gb/s SDI (ST 292-1:2018 §9.5).

These are the original SMPTE HD-SDI VPIDs and the basis of all later 3G/6G/12G family
extensions. Their current implementations have accumulated several discrepancies against the
2017+ revisions of ST 292-1 that explicitly added Transfer Characteristics signalling, modern
colorimetry, ICTCP, and 10-bit Full Range support.

## Findings

### P1: BIT_DEPTH_HD_1080 swaps 2h ↔ 3h vs ST 292-1:2018 §9.5.4

The current `BIT_DEPTH_HD_1080` constant maps:

```
0h → "8-bit"
1h → "10-bit"
2h → "10-bit Full Range"
3h → "Reserved"
```

…but ST 292-1:2018 §9.5.4 (and the matching Table 5 byte 4 column) explicitly defines:

```
0h → 8 bits per sample
1h → 10 bits per sample
2h → Reserved
3h → 10 bits per sample with full range coding (BT.2100)
```

So codes 2h and 3h are **silently swapped**. A genuine 10-bit Full Range payload (`b1:b0 = 3h`)
is mis-displayed as "Reserved", and a Reserved value (`2h`) is mis-displayed as "10-bit Full
Range". Worse, no warning is emitted for the Reserved case.

Probe evidence:

```
--- 85 CA 00 02  (b1:b0 = 2h Reserved per §9.5.4) ---
  BD: 10-bit Full Range          <-- WRONG, should be Reserved + warn
--- 85 CA 00 03  (b1:b0 = 3h 10-bit Full Range per §9.5.4) ---
  BD: Reserved                    <-- WRONG, should be "10-bit Full Range"
```

Fix: swap the 2h and 3h entries in `BIT_DEPTH_HD_1080`. The same constant is also referenced
by 0x95 (ST 425-3:2019 §7.2.3.5), 0x96 (ST 425-3:2019 §8.2.3.5) and 0x98 (ST 425-5:2019 §7.2.3.5)
— but in those specs the field has a *different* mapping (10FR / 10 / 12 / 12FR or only 10FR/10
with 2h/3h Reserved). Migrating 0x95 / 0x98 to `BIT_DEPTH_ST372` and 0x96 to a new
`BIT_DEPTH_ST425_3_BDS` table is part of this fix.

### P0: 0x84 / 0x85 round-trip is BROKEN

Same encoder / decoder mismatch pattern uncovered in every previous audit: encoder consumes
raw numeric bit fields but the decoder writes string labels, so the round-trip silently zeros
out everything that wasn't expressible as a JS-coerced number.

Probe evidence:

```
RT 84 4A 00 01: MISMATCH  (got CA 00 01, want 4A 00 01)   <-- encoder hard-codes b7=1
RT 84 4A 00 00: MISMATCH  (got CA 00 00, want 4A 00 00)
RT 84 49 00 01: MISMATCH  (got CA 00 01, want 49 00 01)   <-- 50 Hz
RT 85 CA 00 01: MISMATCH  (got CA 00 00, want CA 00 01)   <-- bit depth string lost
RT 85 06 20 01: MISMATCH  (got 0A 20 00, want 06 20 01)   <-- registry sample
RT 85 CA 00 03: MISMATCH  (got CA 00 00, want CA 00 03)   <-- 10-bit FR
RT 85 DA 00 01: MISMATCH  (got CA 00 00, want DA 00 01)   <-- HLG
RT 85 EA 00 01: MISMATCH  (got CA 00 00, want EA 00 01)   <-- PQ
RT 85 CA 60 01: MISMATCH  (got CA 20 00, want CA 60 01)   <-- 2048×1080
RT 85 CA A0 01: MISMATCH  (got CA 20 00, want CA A0 01)   <-- Rec.2020
RT 85 CA B0 01: MISMATCH  (got CA 20 00, want CA B0 01)   <-- Unknown (split)
RT 85 CA 00 11: MISMATCH  (got CA 00 00, want CA 00 11)   <-- ICTCP
```

Fix: expose raw numeric bit fields (`rate`, `samp`, `colorim`, `tcBits`, `aspectBit`, `hSampBit`,
`signalBit`, `depthBits`, `transBit`, `picBit`) in `characteristics`; update each `encode()` to
prefer the raw fields with backward-compatible string fallbacks.

### P1: 0x84 — Byte 2 b7 mislabeled as "Transport scan"

ST 292-1:2018 §9.4 Table 4 explicitly marks Byte 2 b7 as **Reserved** for 0x84, with the
mandatory value `0`. (720-line is always progressive, so there is no transport-scan distinction
to encode.) §9.4.1 reinforces this:

> The progressive picture flag bit b6 of Byte 2 shall be set to (1);
> The picture rate bits b3 to b0 of Byte 2 shall only use the values as defined in SMPTE ST 296;
> **All other bits shall be Reserved and set to (0).**

The current decoder labels b7 as "Transport scan" (Progressive / Interlaced) and never warns
when it is `1`. This silently masks a spec violation and contradicts Table 4.

Fix: relabel b7 as "Reserved (per §9.4 Table 4)"; emit a warning when `b7 = 1`.

### P1: 0x84 — `decodeScanBits(0, 1, 0x84)` returns "PsF"

The shared `decodeScanBits` helper interprets `b7=0, b6=1` as "PsF" for any layout that isn't
explicitly handled. For 0x84 this is wrong: 720-line is always progressive, and b7 is Reserved
(it does not indicate transport scan). The canonical 0x84 byte 2 b7:b6 = `01` therefore means
"Reserved=0 + Picture progressive=1", i.e. plain Progressive.

Probe evidence:

```
--- 84 4A 00 01  (canonical b7=0 b6=1) ---
  RES: 1280×720 | scan=PsF              <-- WRONG, should be Progressive
```

Fix: hard-set scan = "Progressive" for 0x84.

### P1: 0x84 — missing Byte 2 b6 = 0 warning

Per §9.4.1 *"The progressive picture flag bit b6 of Byte 2 shall be set to (1)"*. The current
decoder emits a generic "HD 720-line is always progressive" message for any `trans||pic = 0`
combination — which fires *also* when b7=0 (the canonical case), producing a spurious warning on
canonical streams. The spec violation is specifically `b6 = 0`.

Fix: replace the generic warning with a strict `b6 != 1` check.

### P1: 0x84 — missing Byte 2 b5 / b4 reserved-bit warnings

Per §9.4 Table 4, byte 2 bits b5 and b4 are Reserved (must be 0). The decoder lumps them as a
single field and emits no warning when they are non-zero. This makes spec violations invisible.

Fix: emit per-bit warnings for `b5 != 0` and `b4 != 0`.

### P1: 0x84 — missing Byte 3 b3:b0 ≠ 0h warning

Per §9.4.2 *"The sampling structure bits b3 to b0 of Byte 3 shall be set to (0) 4:2:2"*. The
decoder happily accepts any sampling code and never warns. A non-zero sampling field for 0x84
is a spec violation.

Probe evidence:

```
--- 84 4A 01 01  (samp = 1h, must be 0h per §9.4.2) ---
  SAMP: 4:4:4 Y'CbCr             <-- silently accepted, no warning
--- 84 4A 07 01  (samp = 7h, must be 0h per §9.4.2) ---
  SAMP: Reserved                  <-- no warning
```

Fix: emit a warning when `samp !== 0x0`.

### P1: 0x84 — missing Byte 3 b7:b4 reserved-bit warnings

Per §9.4 Table 4, byte 3 bits b7:b4 are all Reserved. The decoder lumps them together but emits
no warning when any are set.

Fix: emit a warning when `(b3 >> 4) & 0xF != 0`.

### P1: 0x84 — missing Byte 4 b7:b1 reserved-bit warnings

Per §9.4 Table 4 / §9.4.3, byte 4 bits b7 down to b1 are all Reserved (only b0 is Bit depth).
The decoder lumps them together but emits no warning when any are set.

Probe evidence:

```
--- 84 4A 00 FF  (byte4 all reserved bits = 1) ---
  (no warnings)                   <-- silently accepted
```

Fix: emit a warning when `(b4 >> 1) & 0x7F != 0`.

### P1: 0x85 — Byte 4 b4 (Y'CbCr / ICTCP signal type) is not decoded

ST 292-1:2018 §9.5.3 explicitly defines Byte 4 b4 for 0x85:

> b4 = 0 indicates Y′C′BC′R sampling.
> b4 = 1 indicates ICTCP in accordance with Recommendation ITU-R BT.2100.

The current decoder lumps b7:b2 together as "Reserved", which silently masks the ICTCP
indicator. A genuine ICTCP feed (b4 = 1) is decoded as ordinary Y'CbCr.

Probe evidence:

```
--- 85 CA 00 11  ICTCP (byte 4 b4=1) ---
  signal: -                       <-- silently dropped
```

Fix: split byte 4 into per-bit fields and surface a `signalType` in characteristics.

### P1: 0x85 — missing reserved-bit warnings on Byte 4 b7 / b6 / b5 / b3 / b2

Per §9.5.3 Table 5, Byte 4 bits b7, b6, b5, b3, b2 are all Reserved (must be 0). The decoder
currently lumps them as a single `b7:b2` field with no warnings.

Probe evidence:

```
--- 85 CA 00 80  byte4 b7=1 ---  (no warnings)
--- 85 CA 00 40  byte4 b6=1 ---  (no warnings)
--- 85 CA 00 20  byte4 b5=1 ---  (no warnings)
--- 85 CA 00 08  byte4 b3=1 ---  (no warnings)
--- 85 CA 00 04  byte4 b2=1 ---  (no warnings)
```

Fix: emit per-bit warnings for each.

### P2: 0x85 — colorimetry 1h reported as "Color VANC packet" instead of Reserved

ST 292-1:2018 §9.5.2 enumerates the only defined colorimetry values (split bits b7,b4):

> b7,b4 = 0h identifies Rec 709 colorimetry
> b7,b4 = 2h identifies UHDTV colorimetry (BT.2100 primaries)
> b7,b4 = 3h identifies unknown colorimetry
> Other values are reserved.

The implementation falls back to the global `COLORIMETRY_SPLIT` table, which still reports 1h
as "Color VANC packet" (the legacy pre-2017 ST 425-1 split-bit semantic that ST 292-1 dropped
in its 2018 revision).

Probe evidence:

```
--- 85 CA 10 01  colorim 1h Reserved per §9.5.2 ---
  COLOR: Color VANC packet        <-- should be "Reserved" + warn
```

Fix: in the 0x85 decoder, override the colorimetry label to "Reserved (per ST 292-1:2018
§9.5.2)" when `colorim === 0x1`, and push a warning. Same pattern as 0x87 (ST 372:2017).

### P2: 0x85 — reserved sampling-structure values (Bh / Ch / Dh / Fh) emit no warning

Per Table 6 in §9.5.2, sampling values Bh, Ch, Dh, Fh are all "Reserved". The decoder happily
returns the global `SAMPLING` table label `"Reserved"` but does not push a warning.

Fix: emit a warning for `samp ∈ {Bh, Ch, Dh, Fh}`.

## Resolution

All findings addressed in the same pass:

- `BIT_DEPTH_HD_1080` corrected to ST 292-1:2018 §9.5.4 mapping (8 / 10 / Reserved / 10FR).
- 0x95 and 0x98 migrated to `BIT_DEPTH_ST372` (10FR / 10 / 12 / 12FR per ST 425-3:2019
  §7.2.3.5 / ST 425-5:2019 §7.2.3.5).
- 0x96 migrated to a new `BIT_DEPTH_ST425_3_BDS` table (10FR / 10 / Reserved / Reserved per
  ST 425-3:2019 §8.2.3.5 — only 0h and 1h are defined for B-DS 2160-line).
- 0x84 decoder rewritten to:
  - relabel b7 as Reserved and warn when set;
  - hard-set `scan = "Progressive"`;
  - emit strict `b6 != 1` warning;
  - emit per-bit warnings for byte 2 b5, b4 and byte 3 b7, b6, b5, b4 and byte 4 b7..b1;
  - emit warning when sampling != 0h;
  - expose raw fields for round-trip.
- 0x84 encoder rewritten to default b7 to 0 (Reserved) and prefer raw bit fields.
- 0x85 decoder rewritten to:
  - split byte 4 into per-bit fields (b7, b6, b5, b4 signal type, b3, b2, b1:b0 bit depth);
  - emit reserved-bit warnings for b7, b6, b5, b3, b2;
  - emit warning + override label for `colorim === 1h`;
  - emit warning for reserved sampling values Bh / Ch / Dh / Fh;
  - expose raw numeric bit fields.
- 0x85 encoder rewritten to prefer raw bit fields with string fallbacks.

After the fixes, all probe round-trip cases pass and all expected warnings are emitted.
