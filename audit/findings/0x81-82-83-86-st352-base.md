# Audit 0x81 / 0x82 / 0x83 / 0x86 — SMPTE ST 352:2013 Annex B

| Field    | Value |
| -------- | ----- |
| Family   | Pre-HD legacy SDI VPIDs (SD-SDI / 540 Mb/s SDI / SD-into-HD) |
| Spec     | `audit/pdf-text/st0352-2013.txt` Annex B (Tables B.1 / B.2 / B.3 / B.4.1 / B.4.2)<br>`audit/pdf-text/st0259-2008.txt`, `audit/pdf-text/st0347-2001_stable2006.txt`, `audit/pdf-text/st0349-2001_stable2006.txt` |
| Code(s)  | 0x81, 0x82, 0x83, 0x86 |

## Scope

Four legacy Byte 1 codes — all defined by ST 352:2013 Annex B with byte 2/3/4 layouts taken
from the underlying interface standards (ST 259, ST 347, ST 349). These are the original
"existing-interface" registry codes from before HD-SDI:

- 0x81 — 483/576-line interlaced payloads on 270 Mb/s and 360 Mb/s SDI (ST 352 §B.1)
- 0x82 — 483/576-line extended payloads on 360 Mb/s single-link or 270 Mb/s dual-link SDI (ST 352 §B.2)
- 0x83 — 483/576-line payloads on a 540 Mb/s SDI (ST 352 §B.3, ST 347:2001)
- 0x86 — 483/576-line payloads mapped into 1.5 Gb/s HD-SDI (ST 352 §B.4, ST 349:2001 Tables B.4.1/B.4.2)

## Findings

### P1: All four layouts — reserved-bit violations are silently accepted (no `warnings.push`)

Each decoder annotates its reserved-bit fields with a UI `flag: "warn"` when they are non-zero,
but does NOT push a corresponding entry into the `warnings` array. As a result, the prominent
"Warnings" list shown to the operator stays empty even when the input violates the spec.

Probe evidence:

```
--- 81 86 00 01  b7=1 Reserved per §B.1 ---           (no warnings)
--- 81 36 00 01  b5:b4 nonzero Reserved per §B.1 ---  (no warnings)
--- 81 06 30 01  byte3 b5:b4 nonzero ---              (no warnings)
--- 81 06 00 FE  byte4 b7:b1 nonzero ---              (no warnings)
--- 83 86 05 01  b7=1 Reserved per §B.3 ---           (no warnings)
--- 83 06 70 01  byte3 b6:b4 nonzero Reserved ---     (no warnings)
--- 83 06 05 FE  byte4 b7:b1 nonzero ---              (no warnings)
--- 86 E6 00 01  byte2 b7:b5 nonzero ---              (no warnings)
--- 86 06 F0 01  byte3 b7:b4 nonzero ---              (no warnings)
--- 86 06 00 81  byte4 b7=1 ---                        (no warnings)
--- 86 06 00 21  byte4 b5=1 ---                        (no warnings)
--- 86 06 00 07  byte4 b2:b1 nonzero ---               (no warnings)
```

Fix: emit explicit `warnings.push(...)` calls for every reserved-bit violation in 0x81 / 0x82 /
0x83 / 0x86 (same pattern as the 0x84 / 0x85 / 0x87 fixes).

### P1: 0x81 — Byte 2 b6 = 1 violation is silently accepted

ST 352:2013 §B.1 mandates *"Bit 6 of byte 2 shall be set to a value of 0 to identify an
interlaced payload"*. The decoder annotates the field with "Progressive (invalid for SD-270)"
plus a UI `flag` but emits no warning.

Probe evidence:

```
--- 81 46 00 01  b6=1 Progressive (invalid per §B.1) ---  (no warnings)
```

Fix: emit `warnings.push("ST 352:2013 §B.1 mandates Byte 2 b6 = 0 (interlaced).")` when `b6 = 1`.

### P1: 0x82 — Picture rate validation does not run

Although `allowedRates: [0x9, 0xA, 0x5, 0x6]` is declared, the decoder never invokes the
`!this.allowedRates.includes(rate)` check. A rate of 7h flows through silently.

Probe evidence:

```
--- 82 07 00 01  invalid rate 7h ---                      (no warnings)
```

Fix: add an `allowedRates`/`allowedSamplings` validation pass and emit warnings for any
out-of-set value, matching the 0x81/0x83 pattern.

### P1: 0x82 — Mode cross-validation missing

ST 352:2013 §B.2 defines two distinct modes:

- **Progressive 483/576-line**: rate ∈ `{9h, Ah}`, sampling = `0h` (DL 270 Mb/s) or `3h` (SL 360 Mb/s).
- **Interlaced 4:4:4:4**: rate ∈ `{5h, 6h}`, sampling ∈ `{5h, 6h, 9h, Ah}`.

The current implementation just unions the two sets, so a progressive payload with sampling 5h
(only valid for the interlaced 4:4:4:4 mode) is accepted with no warning.

Probe evidence:

```
--- 82 4A 05 01  progressive with sampling 5h ---  (no warnings)
```

Fix: add a per-mode cross-validation: if `b6 = 1` (progressive), sampling shall be 0h or 3h;
if `b6 = 0` (interlaced), sampling shall be 5h/6h/9h/Ah.

### P0: All four layouts — round-trip is BROKEN

Same root cause as every previous audit: encoders read raw numeric bit fields (`c.rate`,
`c.aspect`, `c.samp`, `c.hSamp`, `c.bitDepth`), but decoders populate string labels into
`c.aspect = "16:9"`, `c.bitDepth = "10-bit"`, `c.horizontalActive = 960` (not `c.hSamp`), and
do not expose the underlying numeric bit values.

Probe evidence:

```
RT 81 05 80 01: MISMATCH  (got 06 80 01, want 05 80 01)   <-- rate string-only
RT 81 06 C0 00: MISMATCH  (got 06 80 00, want 06 C0 00)   <-- hSamp via horizontalActive
RT 82 49 83 01: MISMATCH  (got 4A 80 01, want 49 83 01)   <-- rate / sampling raw
RT 82 06 05 01: MISMATCH  (got 0A 00 01, want 06 05 01)   <-- interlaced 4:4:4:4 mode
RT 83 49 80 01: MISMATCH  (got 46 85 01, want 49 80 01)   <-- ST 347 progressive
RT 86 15 02 11: MISMATCH  (got 15 00 11, want 15 02 11)   <-- ST 349 sampling B.4.2
RT 86 06 05 01: MISMATCH  (got 06 00 01, want 06 05 01)   <-- progressive sampling
```

Fix: expose raw numeric fields (`rate`, `samp`, `aspectBit`, `hSampBit`, `depthBit`, `picBit`,
`channelBit`, `lineCountBit`, `mappingBit`, `b2_*Reserved`, `b3_*Reserved`, `b4_*Reserved`)
in `characteristics`; rewrite each encoder to prefer those fields with string fallbacks.

### P2: 0x83 — Mode cross-validation per ST 347 Table 1

Per ST 347:2001 Table 1, only six (rate × sampling × scan) combinations are defined:

| System | Rate | Sampling                | Scan         |
|-------:|------|-------------------------|--------------|
|   1    | 6h (29.97) | 5h/6h/9h/Ah (4:4:4:4) | Interlaced |
|   2    | 5h (25)    | 5h/6h/9h/Ah (4:4:4:4) | Interlaced |
|   3,5  | Ah (59.94) | 0h (4:2:2)            | Progressive |
|   4,6  | 9h (50)    | 0h (4:2:2)            | Progressive |

The current implementation accepts the *union* of rates and samplings without cross-validating
against the scan bit. This is a P2 because operators may receive non-canonical combinations
that are in spec for the byte ranges but not for any defined system.

Fix: emit a warning when `(b6=1 progressive)` is paired with sampling != 0h, or when
`(b6=0 interlaced)` is paired with sampling = 0h.

### P2: 0x86 — Line-count vs rate cross-validation

Per ST 352 §B.4 + ST 349 Table 1, the (line-count × rate) combinations are constrained:

- 483-line (b4 = 0): rate ∈ `{6h, Ah}`  (30/1.001 interlaced or 60/1.001 progressive)
- 576-line (b4 = 1): rate ∈ `{5h, 9h}`  (25 interlaced or 50 progressive)

The current implementation does not cross-validate.

Fix: emit a warning for any line-count × rate combination outside of the four legal pairs.

### P2: 0x86 — Sampling vs rate cross-validation

ST 349 Table 1 / ST 352 Table B.4.2 implicitly tie the sampling-structure code to the rate:

- Interlaced sampling codes `{0h, 1h, 3h, 4h, 7h, 8h}` require rate `{5h, 6h}` (25 or 30/1.001).
- Progressive sampling codes `{2h, 5h, 6h, 9h}` require rate `{9h, Ah}` (50 or 60/1.001).

Mismatched (rate × sampling-encoded-scan) pairs are not flagged.

Fix: emit a warning for any sampling × rate combination outside the legal sets.

## Resolution

All findings addressed in the same pass:

- 🛠 **0x81 / 0x82 / 0x83 / 0x86 decoders rewritten** to:
  - emit explicit `warnings.push(...)` for every reserved-bit violation (byte 2/3/4 reserved
    fields per ST 352 Annex B Tables B.1 / B.2 / B.3 / B.4.1);
  - emit warnings for mandated bits (e.g. 0x81 Byte 2 b6 = 0; 0x82 cross-mode validation;
    0x83 ST 347 system cross-validation; 0x86 line-count/rate and sampling/rate cross-validation);
  - expose raw numeric bit fields (`rate`, `samp`, `aspectBit`, `hSampBit`, `depthBit`,
    `picBit`, `channelBit`, `lineCountBit`, `mappingBit`, plus the per-byte reserved-bit
    captures used by the encoder for round-trip).
- 🛠 **0x81 / 0x82 / 0x83 / 0x86 encoders rewritten** to prefer the new raw fields with
  backward-compatible string fallbacks.
- 🛠 **Picture-rate validation enabled for 0x82** (was previously declared but never invoked).
- 🛠 **0x86 round-trip preset vectors** in `vpid.html` updated from non-canonical
  `86 15 02 11` and `86 09 09 49` to spec-canonical `86 19 02 11` (576p / 50 Hz / 4:2:0p
  system 12) and `86 19 09 49` (576p / 50 Hz / 4:2:0p ×2ch system 12). Smoke tests in
  `tests/extract_vpid_js.py` updated to match.

## Verification

  emits an explicit warning; all 17 round-trip cases (4 × 0x81 + 4 × 0x82 + 4 × 0x83 +
  5 × 0x86) round-trip identically.
